# Engineering Change Orders — When to Raise One, What Each State Means

## Who this lesson is for

You're the designer or shop lead who notices that something on a cabinet
needs to change — a drawing error, a vendor substitution, a customer
revision, a tolerance the floor can't actually hit — and you have to
move that change through engineering review without breaking the
manufacturing orders already in flight. Every change you make through
PLM rides a paper trail; this lesson is the practical shape of that
trail and what each click commits to the database.

## Where this lives on the site

Sign in at **southbrookcabinetry.space/odoo** with your PLM user
account, then:

> **Southbrook PLM → Change Orders**

Approvers (the people who can push an ECO past the Under Review gate
or hit Apply) also see:

> **Southbrook PLM → Configuration → ECO Types**
> **Southbrook PLM → Configuration → ECO Stages**

These two configuration screens are where the seeded stage pipeline
and the four ECO types live. Approvers rarely touch them — they're
admin-shaped — but they're worth knowing about because if a colleague
adds a new stage and forgets to set `approval_required`, the gate
silently disappears.

There's also a one-click bridge from the rest of the platform: a
small flag-icon button on every line of a sale order's Order Builder
grid (Sales → Quotations → form view → order lines list) calls
`sale.order.line.action_raise_eco()` and opens a draft ECO pre-filled
with the cabinet's BoM, the order/line/product cited in the title,
and `target_kind=bom` already selected. Use it.

## What your screen shows

When you open **Change Orders**, you land on a kanban grouped by
**Stage** (`stage_id` on `southbrook.eco`). Each card shows:

- **Reference** (`name` on `southbrook.eco`) — auto-generated by an
  `ir.sequence` (e.g. `ECO/2026/0017`). Read-only; assigned on create.
- **Title** (`title`) — your one-line summary. This is the field that
  shows up in chatter notifications and on the MO's "Governing ECO"
  link, so write it like the headline of a Jira ticket.
- **Type** (`eco_type_id` → `southbrook.eco.type`) — one of the four
  seeded categories: **Template BoM Revision**, **Cut-Geometry
  Revision**, **Construction-Rule Change**, **Engineering Document
  Update**. The type drives a hidden `target_kind` selection
  (`bom` / `cut_spec` / `rule` / `document`) which in turn drives
  which target field the form shows.
- **Target Kind badge** — derived (`target_kind` is a related/stored
  field). Tells you at a glance what apply will actually do.
- **Priority** (`priority`) — Normal / High / Urgent.
- **Responsible** (`user_id`) — defaults to you on create.

Open a card and you land on the form. The form's notebook has two
pages:

- **Target tab** — one of four fields is visible depending on the type:
  - `bom_id` (m2o to `mrp.bom`) when type is BoM Revision. Required.
  - `cut_spec_id` (m2o to `southbrook.cut.spec`) when type is
    Cut-Geometry Revision. Required.
  - `git_ref` (Char) when type is Construction-Rule Change. Required —
    the rule lives in `config_rules.xml` and git is the system of
    record; the ECO carries the commit SHA or PR URL so the audit
    trail still captures it.
  - `document_ids` (m2m to `ir.attachment`) when type is Engineering
    Document Update. At least one attachment required.

- **Description tab** (`description`, HTML) — what's changing, why, and
  the engineering rationale. This is what an auditor or a future
  designer reads when they ask "why did we do this in 2026?"

Header buttons (visible only while `state == open`):

- **Approve** — stamps `approver_id` and `approval_date`, advances
  one non-terminal stage. PLM Approver group only.
- **Apply Change** — runs the per-kind handler, flips `state` to
  `applied`, lands the ECO in the Applied stage. PLM Approver only.
- **Next Stage** — moves to the next non-terminal stage in sequence.
- **Reject** — flips to `rejected`, lands in the Rejected stage.
- **Reset to Draft** (visible when state isn't open) — clears
  approval bookkeeping and sends the ECO back to the first
  non-terminal stage. Used after a reject when you want another try.

A `web_ribbon` widget marks the form **Applied** (green) or
**Rejected** (red) once it lands in a terminal state.

## Your daily flow

**1. When to raise an ECO at all.**

Raise one whenever you change something that's already governed by
PLM. The four shapes are:

- **Drawing error / customer revision** that changes a template BoM
  → ECO type **Template BoM Revision**. Pick the target `mrp.bom`,
  describe the change, attach the marked-up drawing (PDF or DWG)
  in the Documents tab.
- **Material substitution** that changes the geometric inputs
  every cabinet reads (a panel thickness, a reveal, the rabbet
  depth, the toe-kick height) → ECO type **Cut-Geometry Revision**.
  First create a draft `southbrook.cut.spec` with the new values
  (see lesson 4.2), then point the ECO at it via `cut_spec_id`.
- **Manufacturability fix** that lives in code (a `config_rules.xml`
  exclusion, a Python computed field, a series→door restriction)
  → ECO type **Construction-Rule Change**. The code change lands
  via a git PR; the ECO carries the PR URL or commit SHA in
  `git_ref` and exists *only* to make the audit trail complete.
- **Document-only update** (a refreshed vendor cut sheet, a new
  hardware spec PDF, an updated shop drawing) → ECO type
  **Engineering Document Update**. Attach the document(s) and apply.

If the change doesn't touch a template BoM, the parametric cut spec,
a construction rule, or an engineering document — you don't need an
ECO. Updating attribute display order on a product template is a
plain `write`, not a PLM event.

**2. Drafting (the loop).**

- From **Change Orders**, click **New**. The kanban pre-creates
  the record in the **Draft** stage (`sequence=10` on
  `southbrook.eco.stage`).
- Pick the **Type**. Watch the form react — the Target tab swaps
  to the right field.
- Fill the target. For a BoM ECO, browse to the canonical template
  BoM (the cabinet's active version). For a cut-spec ECO, the
  draft cut spec you authored separately.
- Write the **Title** like a commit message: imperative, terse,
  scoped. "Bump base-cabinet back panel from 6.35 mm to 9 mm" beats
  "back panel change."
- Fill the **Description** with the why. Auditor-ready.
- Save. The reference (`ECO/YYYY/NNNN`) gets assigned now.

**3. Moving it through the pipeline.**

The seeded stages are:

| Sequence | Name | Flags | What gates here |
|---|---|---|---|
| 10 | **Draft** | — | Anyone can edit. No effect committed. |
| 20 | **Under Review** | `approval_required=True` | Leaving this stage requires PLM Approver rights. |
| 30 | **Approved** | — | The change has approval but the handler hasn't run yet. |
| 40 | **Applied** | `is_applied_stage=True`, `is_final=True`, `fold=True` | Terminal. The handler ran; effect committed. |
| 50 | **Rejected** | `is_rejected_stage=True`, `is_final=True`, `fold=True` | Terminal. No effect committed. |

The `state` field (`open` / `applied` / `rejected`) tracks the
lifecycle outcome separately from the configurable kanban stage. You
get both because shop leads sometimes want to add a custom
"Awaiting Vendor Quote" or "Customer Approved" stage between Under
Review and Approved without breaking the apply handlers — those
look at `state`, the kanban looks at `stage_id`.

- **Click Next Stage** to move Draft → Under Review. No
  approver rights needed.
- **Click Approve** (Approver group only) at Under Review to advance
  past the gate. This stamps `approver_id` and `approval_date` and
  moves you to Approved.
- **Click Apply Change** (Approver group only) at Approved. This is
  the irreversible click. It runs the per-kind handler:

  - **BoM ECO** (`_apply_bom`): `sudo()`-copies the target BoM to
    a new `southbrook_version`, archives the prior version
    (`active=False`), links the new one as `new_bom_id`, and posts a
    chatter line citing both versions.
  - **Cut-spec ECO** (`_apply_cut_spec`): calls
    `southbrook.cut.spec.action_activate()` on the candidate, which
    flips it to `state=active` and supersedes the prior active
    spec. Exactly one cut spec can be active at any time — enforced
    by the `_check_single_active` constraint.
  - **Rule ECO** (`_apply_rule`): record-only; chatter cites the
    `git_ref`. The rule itself lands when the PR merges.
  - **Document ECO** (`_apply_document`): record-only; chatter
    counts the attached documents. Refuses to apply with zero
    attachments.

  After the handler, the ECO writes `state=applied`, stamps
  `applied_date` (and `approver_id`/`approval_date` if a prior
  Approve click hadn't already), and lands in the Applied stage.

**4. Rejecting or withdrawing.**

- **Reject** is the right action on an ECO that shouldn't ship. It
  flips `state` to `rejected` and lands in the Rejected stage. It
  cannot be used on an already-applied ECO — the apply handler has
  already mutated the database, and Reject is not an undo. The
  system raises a UserError if you try.
- **Withdrawal** — there isn't a separate "Withdrawn" state. Use
  Reject with a chatter note explaining the withdrawal. If you
  later want to try the same change, click **Reset to Draft** to
  send it back to the first non-terminal stage; this clears
  `applied_date`, `approver_id`, and `approval_date` so the next
  pass through stamps cleanly.

**5. End-of-shift housekeeping.**

- Filter the kanban with **My ECOs** (`user_id = uid`). Any cards
  stuck in Under Review for more than a day are blocking someone.
- Cards in Approved without an Apply click are the danger zone —
  the change has been signed off but the BoM hasn't versioned yet,
  so MOs released after the approval are still pulling the old
  BoM. Apply or reset.

## Common mistakes + how to recover

**"I clicked Apply on a BoM ECO and now an MO that's already in
flight is showing the old BoM version on its form."**

That's correct — and intentional. The Apply handler copies the BoM
to a new version and archives the old one, but MOs already confirmed
hold a pointer to the BoM that was active at the time of confirm.
The MOs in flight finish on the spec they were planned against; the
new version takes effect on the *next* MO created from this product
template. If the change is so urgent that in-flight MOs must follow
the new spec, you have two options: cancel and re-create the MOs
against the new BoM (planner's call), or raise a follow-up
work-order amendment manually on each affected MO. The system will
not silently re-base them.

**"I rejected an ECO that had actually been Applied yesterday — now
the audit trail says 'rejected' but the BoM is still on the new
version."**

You can't. The system blocks Reject on an applied ECO with
`UserError("ECO %s is already applied — its change is committed…")`.
The check exists because an early demo allowed this and produced a
record that lied about the outcome. If you actually need to undo
an applied change, raise a *new* BoM ECO whose target is the new
version and whose effect rolls the values back to the original.
That's the only honest way — and the audit trail captures both
events.

**"I tried to drag an ECO straight into the Applied column on the
kanban to skip the buttons."**

The `write` method blocks it. The terminal-stage guard checks that
any direct write of `stage_id` to a stage flagged `is_final` must
arrive in the same `write()` call with a matching `state` value
(`applied` or `rejected`). A kanban drag writes only `stage_id`, so
it raises a UserError that points you back at Apply or Reject. The
guard exists because skipping the buttons skips the per-kind
handlers — your BoM doesn't version, your cut spec doesn't activate
— and the ECO record ends up in a paradoxical
`stage=Applied, state=open` shape. Click the buttons.

**"I clicked Apply but the BoM ECO failed with 'AccessError: cannot
create mrp.bom'."**

This was a real install-time bug. The fix is to ensure your PLM
Approver group has been seeded correctly — the apply handler does
`old.sudo().copy(...)` because PLM Approver isn't necessarily a
Manufacturing Administrator, and the approval-gate authorisation
is what authorises the BoM mutation. If you still hit this on
your install, check that
`southbrook_plm.group_southbrook_plm_approver` is assigned to your
user and ask an admin to upgrade the module.

**"I rejected an ECO, then realised I shouldn't have. I tried to
Apply it but got an error."**

Correct path: click **Reset to Draft**. That moves the ECO back
to the first non-terminal stage with `state=open` and clears the
approval bookkeeping. Then re-approve and apply. The reset itself
posts a chatter line so the audit trail captures the reversal
explicitly — Apply refuses to silently revive a rejected ECO
because rejection is a deliberate decision worth a paper trail.

## What the system is doing behind the scenes

Every action you take writes to `southbrook.eco` (the change order
itself) and posts a `mail.thread` message — the form inherits
`mail.thread` and `mail.activity.mixin`, so chatter is the audit
substrate.

The Apply handler's branching is determined by
`eco_type_id.target_kind` (a stored related field). For
**BoM** kind, the handler does `old.sudo().copy({...})` on
`mrp.bom`, bumping a custom `southbrook_version` integer the
estimating addon adds to `mrp.bom`; the prior BoM is archived
(`active=False`) but never deleted, so any MO that references it
still resolves. For **cut_spec** kind, the handler delegates to
`southbrook.cut.spec.action_activate()`, which both flips the
candidate to `state=active` and writes `state=superseded` on the
prior active spec — keeping the "exactly one active" invariant
that the cut-math seam `mrp_bom._get_cut_constants()` relies on.

The kanban-stage write guard lives in `southbrook.eco.write()`. It
intercepts any write that touches `stage_id`, checks two things —
(a) is the destination stage `approval_required`? if so, require
the PLM Approver group; (b) is the destination stage `is_final`?
if so, require the matching `state` value to be in the same write
— and raises UserError otherwise. Both rules are why Apply and
Reject co-write `state` and `stage_id` together rather than
separately.

The line-to-ECO bridge button on the order builder
(`sale.order.line.action_raise_eco`) opens a new ECO with
`default_eco_type_id`, `default_bom_id`, `default_title`, and
`default_description` set in the action context, so creating an
ECO about a specific sale-order line is one click + Save.

## Quiz (5 questions, applied)

**1.** A customer calls and asks you to switch their full-overlay
hinges to inset on three already-confirmed MOs. You raise a BoM
ECO and click Apply. The customer calls back the next day to
confirm the inset hinges have shipped — but the MOs you saw on the
floor today were still showing the old BoM. What's going on?

> Apply versioned the *template BoM*, but MOs confirmed before the
> Apply hold a pointer to the BoM revision that was active at
> confirm time. The new revision applies to the *next* MO created
> from this product template, not retroactively. To push the
> change through the in-flight MOs, you have to cancel and recreate
> them (planner's call) or amend each MO's work orders manually.
> The platform won't silently re-base in-flight production.

**2.** You start drafting a Cut-Geometry Revision ECO to bump the
shelf ventilation gap from 12.7 mm to 15 mm. The form's Target tab
is asking you for a "Candidate Cut Spec." You don't have one —
you've never authored a cut spec record. What's the right next step?

> Save the ECO as a draft, then go to **Southbrook PLM → Cut
> Specifications**, click **New**, fill in the new constant
> values (carry over all the others from the currently-active
> spec), save it in `state=draft`. Come back to the ECO, point
> `cut_spec_id` at the new draft, and then advance the ECO
> through Under Review → Approved → Apply. Apply will call
> `action_activate` on the candidate and supersede the previous
> active spec. The cut spec is the artifact; the ECO is the
> governance around activating it.

**3.** You try to drag an ECO card from the Approved column
straight to the Applied column on the kanban. The system refuses
with a UserError. Why does the guard exist, and what's the right
action instead?

> Dragging would write only `stage_id`, leaving `state=open` while
> the kanban shows Applied — paradoxical and worse, the apply
> handler (BoM copy / cut-spec activate / etc.) wouldn't run, so
> the engineering effect *isn't actually committed*. The guard
> blocks the bypass; the right action is to click the **Apply
> Change** button in the header, which runs the handler AND
> co-writes both `stage_id` and `state` in a single `write()` call.

**4.** A PLM Approver rejected an ECO that was actually correct;
the engineer has just convinced them it should have been applied.
Walk through the exact clicks to land the change cleanly without
losing the audit trail.

> Open the rejected ECO. Click **Reset to Draft** — this clears
> `applied_date`, `approver_id`, `approval_date`, sends the ECO
> to the first non-terminal stage, and posts a "Reset to draft
> by X" chatter line. Click **Next Stage** to move it back to
> Under Review. The Approver clicks **Approve** (stamps fresh
> approval), then **Apply Change**. The chatter now shows both
> the original reject AND the reset AND the new approval/apply —
> a complete, honest history.

**5.** You're cleaning up a backlog and notice three Construction-
Rule ECOs that have been sitting at Approved for two weeks. You
check git — the PRs they reference were merged the same day each
ECO was approved. What should you do?

> Apply them. The Construction-Rule apply handler is record-only —
> it posts a chatter line citing the `git_ref` and flips state to
> Applied. It doesn't *cause* the code change (git does that); it
> closes the audit loop so an outside auditor can see that
> commit ABC123 was reviewed, approved, and acknowledged-as-shipped
> by PLM. Leaving these at Approved indefinitely leaves the audit
> trail incomplete — the merged code is live in production but
> PLM hasn't formally acknowledged it.
